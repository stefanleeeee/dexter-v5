## Результат 1.7 — управляемая отмена (2026-11-06)

1.7 реализована; 124 автоматических теста (91 регрессионный + 33 новых) прошли. Полная сборка ESP-IDF v6.1 / ESP32-S3 успешна: build/dryer-v2.bin, 0xc9f00 байт, 21% раздела свободно. Подтверждённая проблема до изменения: отмена CommandSession существовала только для disconnect; отдельного локального сигнала, CANCEL/подтверждения и очистки уже скопированных в DMA данных не было. Очистка одной программной очереди не прекращала физический вывод.

Отмена: в консоли запущенного server.py ввести `cancel` или `отмена` и Enter. Отдельный console reader вызывает CancelControl.cancel_current → CommandSession.request_cancel(expected_id=...). Голосовое прерывание не добавлено. При недоступном stdin остаётся программный интерфейс. Сигнал привязан к текущему ID команды/соединению, повторный сигнал идемпотентен. Во время STT/LLM/отдельного вызова Silero отмена кооперативная: уже начатый SDK/model вызов не прерывается, его поздний результат не отправляется; следующая команда ждёт безопасного выхода и общего pipeline lock. Уже сохранённая история разговора не откатывается.

Wire header и PCM сохранены. Добавлены CANCEL 0x15 Python→ESP и CANCELLED 0x16 ESP→Python, payload ровно 32 байта: UUID соединения (16) + счётчик ответа (16), как START/EOS/DONE. Worker остаётся единственным Python writer, основной reader маршрутизирует оба ACK. Отмена заканчивает текущий TCP-кадр до отправки CANCEL; normal DONE после принятой отмены отвергается. Если normal DONE уже принят до сигнала, отмена завершённого ответа отклоняется. До фактического START отмена не посылает неизвестный ESP ID.

ESP меняет generation, очищает программный PCM и pending TCP staging. Только playback consumer завершает текущий ограниченный I2S write, отключает TX, заполняет нулями всю существующую DMA память через preload и включает тот же канал (сброс FIFO драйвером). Затем ждёт свежий DMA EOF-барьер нулевого вывода; только после него TCP task отправляет CANCELLED. Старые scratch/PCM/START не могут возобновить ответ: в framed-соединении требуются тот же connection prefix и возрастающий counter, PCM после отмены без нового START отвергается. Legacy поведение до первого framed START сохранено. Частоты, форматы, размер очереди и настройки I2S не менялись.

Срок отмены после назначения playback ID — 2 s, включая watchdog при блокирующей передаче; без подтверждения закрывается TCP с abortive fallback, это не успешная отмена. ESP disconnect тоже запрашивает очистку DMA. Строгая акустическая задержка не гарантирована: CANCEL идёт после уже переданных TCP данных, fallback зависит от обнаружения разрыва устройством. Ошибка disable/preload/enable не выдаёт success ACK; фиксируется sticky playback error, требуется Reset ESP. Это намеренная защита от повторного запуска частично очищенного DMA. Mutex не удерживается во время driver calls; TCP не вызывает I2S.

Проверено автоматически: отмена до/во время START, STT/LLM/TTS, PCM send, EOS/ACK wait; целостность кадров; повторная команда на том же соединении; устаревшие ID/таймеры/ACK; normal ACK против отмены; disconnect/Reset-подобное закрытие socket; медленная/заблокированная отправка и deadline; очистка queue/DMA, поздний write, отсутствие EOF, ошибки reset API и запрет старого PCM/START. ### Согласованный протокол 1.6

Заголовок остаётся `[type:u8][length:u32 big-endian]`, PCM не меняется. В режиме 1.6:

| Тип | Направление | Payload |
| --- | --- | --- |
| 0x11 START | Python → ESP | 32 байта идентификатора ответа |
| 0x12 PCM | Python → ESP | Прежний raw mono PCM16 LE 24 kHz, прежние лимиты/пакеты |
| 0x13 STOP/EOS | Python → ESP | Те же 32 байта; после него PCM этого ответа больше не принимается |
| 0x14 DONE ACK | ESP → Python | Те же 32 байта, только после успешного завершения; отдельного success/status-поля нет |
| 0x02 MIC | ESP → Python | Прежний raw mono PCM16 LE 16 kHz |

ID = 16 байт UUID поколения Python-соединения + 16 байт возрастающего big-endian счётчика ответов этого соединения. ID непрозрачен для ESP; он сравнивается/возвращается побайтно. Каждый ответ в одном соединении имеет другой счётчик, новое соединение — другое поколение. Эти ID — корреляция, не аутентификация. Логи показывают младшие четыре байта счётчика для удобства: после reconnect отображаемый номер может снова быть 00000001; защита использует весь 32-байтный ID, не это сокращение.

**Обновлять сервер/session_runtime и ESP прошивку вместе.** Новый сервер требует ACK и не имеет молчаливого fallback на send-complete. Старая прошивка не понимает START/STOP с телом 32 и закроет соединение; новая версия сервера с ней не считается рабочей парой. Новая ESP сохраняет legacy START/STOP с нулевым payload и прежний PCM для старого сервера, но legacy не подтверждает окончание. Расширение возможно согласованно на обеих сторонах и было явно разрешено текущим заданием; старые типы и аудиоформат сохранены.

### Когда именно возникает завершение

- Python worker после неизменённого синтеза отправляет START/PCM/настоящий STOP и ждёт ACK. Главный reader продолжает читать и отбрасывать MIC в PROCESSING, а 0x14 разбирает независимо от этого режима. Вторая читающая сокет нить не создавалась.
- Consumer ESP доходит до EOS только после обработки всей software queue и завершения последнего i2s_channel_write. EOS, пришедший во время записи, не может сам выставить ACK-ready.
- После последней записи consumer снимает атомарный snapshot счётчика аппаратных `on_sent` EOF. Затем ждёт **новые** `2 * ceil(total_dma_buf_size / event.size) + 2` EOF: два оборота DMA плюс дополнительный запас нулевого вывода. total DMA size берётся из i2s_channel_get_info, event size — из настоящего callback; это не sleep по длительности текста. Завершившиеся до последней записи EOF не засчитываются. Переполнение uint32 counter проверено тестом.
- Единственное изменение I2S behavior — `auto_clear_after_cb=true` для TX и регистрация on_sent перед enable. Частоты, GPIO, data width, dma_desc_num/dma_frame_num и queue capacity **не менялись**. Необходимость: без очистки circular DMA может повторять PCM после EOS; нельзя делать корректность короткого допустимого PCM-ответа зависимой от неявного хвоста тишины конкретного TTS. Существующие 250 ms тишины в Silero не удалены и синтез не менялся. Основание: локальный ESP-IDF i2s_common.c (TX callback/auto_clear/i2s_channel_write) и [официальная семантика on_sent/auto_clear](http<local-path>).
- Consumer выставляет только ACK-ready. Сокет по-прежнему пишет только TCP task, целым фреймом 0x14 с исходным ID, между целыми mic-фреймами. После получения подходящего ACK worker завершается; основной reader по его done-event возвращает WAKE_WORD и логирует `[PLAYBACK DONE]`. Сам sendall/STOP не завершает PROCESSING.
- Это подтверждение завершения цифрового I2S/DMA-тракта с консервативным запасом, **не измерение звукового давления/аналогового затухания динамика**. Фактическую привязку к слышимому окончанию нужно проверить на плате; при наличии анализатора — по I2S DOUT/BCLK и временам логов.

Ошибки и ограничения:

- Firmware EOS/DMA-wait ограничен 10 s; Python ждёт ACK не более 10 s после отправки STOP. Timeout закрывает/инвалидирует соединение, не отмечается как успех. Reset/disconnect будят worker через cancellation event; событие закрытия не считается ACK. Уже выполняющиеся модельные вызовы сохраняют прежние ограничения 1.2.
- ACK неправильного ID, ранний ACK до EOS, ACK предыдущего ответа и старого соединения не завершают текущий. Некорректная длина ACK закрывает поток, исключая разбор остатка тела как следующего заголовка. Повторный/несогласованный START/EOS на ESP отвергается; новые metadata читаются пошагово с прежними deadlines, mic uplink не блокируется их ожиданием.
- Ошибка I2S или отсутствие DMA EOF не выдаёт success ACK; ESP закрывает соединение по playback_error/EOS timeout, Python завершает ожидание с ошибкой. Consumer/queue reset защищён поколением, старый drain/ready ACK очищается при reconnect. Нового механизма прерывания ответа по голосу/команде не добавлено.
- Нельзя делать из ACK вывод о распознавании команды или качестве произнесения; история Groq и генерация речи не изменены. Legacy-pair/смешанные версии не дают гарантию ACK 1.6.

Изменено только в рамках 1.4:

- В ESP connect выполняется non-blocking с select/SO_ERROR и общим сроком 10 s, после успеха исходные blocking flags восстанавливаются. При частично принятом downlink-header отправка ограничивается также его оставшимся сроком. Ошибка/тайм-аут не продолжают оборванный кадр на новом соединении.
- Полностью пустой downlink не получает idle-deadline: молчание сервера во время STT/LLM/TTS законно. Без heartbeat невозможно отличить такого занятого peer от peer, который продолжает принимать mic, но больше не отвечает. Остановившийся mic consumer обнаруживается по backpressure/send deadline после заполнения TCP-буферов, не обязательно через 10 s от момента его зависания.
- У socket теперь один владелец — TCP task, локальный fd. Mic producer получает состояние connected и поколение под mutex, снимает generation **до** I2S read. При выходе/входе в connected ringbuffer очищается под тем же mutex. Нельзя дописать старую in-flight запись после очистки или поместить preconnect audio в новое соединение. Mutex не удерживается во время I2S read; внутри enqueue сохранён максимум ожидания ringbuffer 10 ms. Программная mic queue очищается, I2S DMA/RX FIFO и уже воспроизводимый TX специально не сбрасываются.

## Критические проблемы

1. **P1 — управление состояниями.** Перепроверка server.py:264–273 опровергла предыдущую формулировку «worker на каждом кадре». Worker запускается внутри условия завершения, но вне проверки минимальной длины. Финальный else привязан к цепочке состояний; остаток уже накопленных кадров после перехода в PROCESSING может вернуть WAKE_WORD до завершения обработки. Реальная частота и сценарий требуют теста.
2. **P2 — общие ресурсы и отправители.** Нет единственного владельца conn/state/истории/Silero и защиты lifecycle worker; возможные пересекающиеся обработчики используют одинаковые WAV одной сессии. Нет отмены при disconnect.
3. **P3/P5 — TCP на ESP.** Короткий положительный send не добирается; malloc failure оставляет payload в потоке, результаты I2S write не проверяются. Рассинхронизация возможна по коду, но не воспроизводилась в этой сессии.
4. **P4/P6/P7 — playback и соединение.** Приём тела, блокирующая запись I2S и mic uplink совмещены; возможны потери mic queue. STOP лишь логируется сервером; подтверждения завершения, отмены и AEC нет. Очередь сохраняется при reconnect, worker не привязан к поколению соединения.
5. **P8/P9 — данные/окружение.** Переполнение abs(int16), отсутствие clipping и обрезка длинных предложений; неполный requirements, относительные пути, секреты в коде. Значения секретов в документацию не перенесены.

Подробные основания, параметры и границы доказательства — [ARCHITECTURE.md](ARCHITECTURE.md). Блокирующее I2S write само по себе не доказывает дефект звука; подтверждено совмещение задач, а величину задержек/потерь нужно измерить.
